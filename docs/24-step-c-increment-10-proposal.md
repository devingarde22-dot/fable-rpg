# Increment 10 — Defense Slot Runtime (superseded proposal)

**Статус:** `SUPERSEDED`. Этот узкий кандидат заменён согласованным полным headless vertical slice в [DR-C-010](./25-step-c-increment-10-full-headless-slice.md); дальнейшую реализацию сверять с DR-C-010.
**Предлагаемая область:** отдельный runtime-слот карты защиты для headless engine в `packages/rules`.
**Кандидат Decision Record:** DR-C-010 (номер предварительный; не считать подтверждённым до решения пользователя).

## Почему этот кандидат

Подтверждённые правила DECK-003 и DECK-004 предусматривают отдельный слот одной карты защиты: при входе в бой герой получает до пяти обычных карт и одну карту защиты; после розыгрыша карта защиты уходит в сброс, а слот может получить следующую карту. DECK-005 требует сохранять каждый экземпляр карты в одном из контейнеров. В спецификации Step C уже есть инвариант, что защитный слот содержит только `cardType=defense`, но текущий runtime не хранит такой слот. Increment 6–7 реализовали обычный card play и цикл обычной руки, оставив defense slot вне scope.

Это делает слот защиты наиболее прямым кандидатом на следующий ограниченный headless increment. Альтернативы — например, активация `reposition` — сейчас менее определены: его template остаётся draft/deferred, а поведение handler не утверждено.

## Предлагаемая цель

Подготовить минимальную основу runtime для одного отдельного слота защиты на героя, не расширяя Increment 10 до production card catalog, балансировки или нового вида защитного эффекта.

### В предварительный scope входит

- добавить отдельное nullable состояние `defenseSlot` для героя, не смешивая его с обычной рукой из максимум пяти карт;
- включить карту в слоте в инвариант уникальности card instance между всеми поддерживаемыми зонами;
- валидировать, что в слоте может находиться только карта с `cardType=defense`;
- определить и проверить атомарные события назначения и снятия карты со слота, включая контракты, snapshot, replay и canonical `stateHash`;
- использовать только явно маркированные `TEST_ONLY / NON_BALANCE` fixtures;
- добавить unit, integration, replay, schema и fixed-seed regression tests для выбранных пользователем правил;
- сохранить существующий deterministic RNG/replay подход и не менять правила обычной руки из DR-C-007.

### В scope не включать без отдельного решения

- production card catalog, реальные значения карт и баланс;
- новый защитный эффект, поглощение/снижение урона или автоматическое срабатывание карты;
- UI/projections, WebSocket/Colyseus, persistence, authentication, deployment и AI;
- новые statuses, новые enemy/intent handlers или изменение `reposition`;
- изменения `fable.damage.v1` или правил обычной руки.

## Решения, блокирующие окончательное утверждение

DECK-003/004 задают назначение слота, но не определяют следующие runtime-правила. Их нельзя выводить из контракта или придумывать при реализации.

1. **Источник и фильтр выдачи.** Защитные карты берутся из общего `drawPile` по `cardType=defense` или из отдельного пула? Как они взаимодействуют с mode filter и контейнером `excludedForMode` из DR-C-007?
2. **Начальная раздача.** Заполнять слот при каждом входе из `movement` в `melee`/`ranged`, только один раз при начале боя или по иному событию? Что происходит, если защитных карт нет?
3. **Пополнение после розыгрыша.** Какой источник и момент используются для получения следующей защитной карты? DECK-004 говорит «по правилам раздачи», но отдельное правило раздачи защитных карт ещё не зафиксировано. Должна ли обычная 300-tick ротация руки когда-либо менять defense slot?
4. **Розыгрыш и эффект.** `player.play_card` в текущей реализации ограничен картами с `direct_damage`; поле эффекта в `CardTemplate` не описывает защитный эффект. Что делает защитная карта: блокирует заранее выбранную атаку, снижает урон, даёт статус, или имеет иной эффект? Разыгрывается ли она как команда игрока либо срабатывает автоматически?
5. **Порядок боя.** Если защитная карта предназначена для ответа на атаку, требуется определить окно/приоритет относительно enemy intent resolution и возможность одновременных команд в одном batch.
6. **Стоимость и ограничения.** Нужны решения о stamina cost, допустимом режиме, цели/тайминге и взаимодействии с immobilized/другими статусами. Текущие confirmed rules не задают их для defense cards.

## Предварительные критерии приёмки после фиксации правил

- В snapshot каждого героя присутствует ровно один отдельный слот, который может быть пустым.
- Обычная рука по-прежнему имеет максимум пять карт; карта защиты не занимает место в ней.
- Каждый card instance существует ровно в одной зоне; некорректный тип в defense slot отклоняется.
- Назначение, использование и пополнение (если утверждены) атомарны, детерминированы и полностью проверяются replay reducer-ом.
- Live simulation, event replay и journal replay дают одинаковые snapshots и `stateHash`.
- JSON Schemas и Ajv покрывают новые события; фиксированные fixtures имеют метку `TEST_ONLY / NON_BALANCE`.
- Полные `pnpm check`, `pnpm build`, canonical schema tests и `git diff --check` проходят.

Эти критерии предварительные и должны быть уточнены после ответов на блокирующие вопросы. Они не подразумевают конкретные gameplay semantics.
