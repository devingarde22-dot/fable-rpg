# Fable — Product Constitution

**Версия:** 0.1  
**Статус:** CONFIRMED  
**Дата:** 2026-10-27  
**Источник:** GDD Fable, подтверждённые решения владельца проекта

## 1. Назначение документа

Этот документ фиксирует неизменяемое продуктовое ядро Fable. Он нужен человеку, AI-разработчику, дизайнеру, программисту и тестировщику, чтобы понимать, **какую игру мы строим**, а не только какие отдельные механики в ней существуют.

Если техническое решение противоречит этому документу, оно требует отдельного Decision Record. ИИ не имеет права молча выбирать трактовку.

## 2. Игра

**Fable** — кооперативная партийная RPG для **2–4 игроков и одного GM**. Баланс первого vertical slice рассчитан на **4 игроков**, но сервер и интерфейсы поддерживают диапазон 2–4.

Игроки находятся в одной комнате, но получают разные уровни информации:

- **TV** показывает общий публичный мир: карту сцены, клетки, персонажей, намерения, таймеры, публичные эффекты и результаты.
- **Телефон игрока** показывает личное состояние героя: игровые карты действий, карту защиты, HP, стамину, статусы, доступные цели, режим и личные сообщения от GM.
- **Планшет GM** показывает полное состояние сцены, скрытые данные, редакторы, журнал, последствия, NPC, checkpoint и rollback.

Главная фантазия: партия принимает решения вместе, но каждый игрок обладает только частью информации. Экипировка, навыки, статусы и личные открытия определяют, что герой может сделать и как он понимает происходящее.

## 3. Игровой loop

```text
Город
→ подготовка героя и ресурсов
→ выбор маршрута
→ узел экспедиции
→ сцена
→ бой / исследование / переговоры / событие
→ решение GM о последствии
→ обновление мира и журнала
→ checkpoint или возвращение в город
```

В одном узле может быть несколько сцен. Сцену можно пропустить, если это разрешено шаблоном узла; пропуск записывается в журнал экспедиции.

## 4. Неизменяемые принципы

### 4.1 Сервер — источник истины

Клиент отправляет намерение команды. Сервер проверяет права, актуальное состояние, режим, дистанцию, клетку, цель, стамину, таймеры и revision. Только сервер создаёт подтверждённое событие.

Клиент не может сам установить HP, результат урона, доступность карты, открытие узла, награду или статус.

### 4.2 GM сохраняет авторство

AI Copilot может искать противоречия, писать варианты текста, предлагать последствия, NPC и команды. AI не является источником истины и не применяет state-changing commands без явного подтверждения GM.

Диалоги ведёт GM. AI может предложить реплики и скрытые подсказки, но не говорит с игроками самостоятельно.

### 4.3 Скрытое не должно утекать

GM-only данные не передаются игроку через snapshot, ошибку, animation payload, reconnect, журнал, AI-контекст или timing-информацию. Для каждого DTO и события существует field-level visibility.

### 4.4 Каждое важное решение обратимо на уровне проекта

Игровой rollback полностью восстанавливает выбранный checkpoint. Технический audit сохраняется только GM для диагностики. Откат не должен дублировать награды или оставлять мир в частично старом состоянии.

### 4.5 Документированное правило важнее устного предположения

Каждое правило, которое влияет на код, должно иметь стабильный Rule ID, статус и хотя бы один тестовый пример.

## 5. Мир и канон

- Игра называется **Fable**.
- Королевство называется **Аверенн** — CONFIRMED.
- Столица — **Вайрмонт**.
- Начальный город — **Миревальт**.
- «Лиловая Гарь» — внутриигровой термин катаклизма, не название игры.
- Происхождение Гари и Три Потери могут оставаться неполностью раскрытыми.
- Лор не изменяется случайным текстом AI. Новые канонические факты проходят через GM и Decision Record.

## 6. Scope первого vertical slice

Первый playable-срез не пытается реализовать всю кампанию. Он включает:

- 3 героев в reference-сценарии при общей балансной цели 4 игроков;
- город Миревальт;
- один маршрут;
- один клеточный узел;
- одну обязательную сцену;
- карту 9×9;
- 2–3 типа врагов;
- игровые карты, защитный слот, HP, стамину и два основных статуса;
- TV, Player и GM проекции;
- намерения врагов и кольцевой таймер;
- одно consequence;
- checkpoint, завершение, поражение, отступление и rollback.

Не входят в первый slice: полноценная кампания, все города Аверенна, AI-автоприменение, процедурная генерация, все классы, ремесло, PvP и production-scale deployment.

## 7. Технологические границы

Игровое ядро должно работать headless и не зависеть от UI, базы данных или AI. Рекомендуемая реализация:

- TypeScript для общего кода;
- WebSocket/Colyseus для комнаты;
- PostgreSQL + Drizzle для persistence;
- JSON Schema + runtime validation;
- Vitest для unit/simulation tests;
- Playwright для e2e;
- фиксируемый server seed для replay.

Конкретная библиотека может быть заменена ADR, если сохраняются контракты и тесты.

## 8. Статусы документов

- `CONFIRMED` — утверждено и может реализовываться.
- `PROPOSAL` — рабочее предложение, код не должен считать его каноном без task-level решения.
- `SUPERSEDED` — заменено более новым правилом, сохраняется только для истории.
- `IMPLEMENTED` — подтверждённое правило реализовано и покрыто acceptance tests.
- `OPEN_QUESTION` — обнаружено противоречие или недостающее решение.

## 9. Правило для AI-разработчика

ИИ обязан:

1. Прочитать этот документ и связанные contracts.
2. Назвать файлы, которые собирается изменить.
3. Не менять CONFIRMED-правила без ADR.
4. Добавить тесты на каждое изменённое правило.
5. Вернуть список допущений и открытых вопросов.
6. Остановиться при конфликте документов, а не угадывать.
