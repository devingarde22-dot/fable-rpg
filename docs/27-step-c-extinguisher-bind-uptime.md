# DR-C-012 — Extinguisher bind eligibility и uptime

**Статус:** `APPROVED — IMPLEMENTED`
**Область:** только eligibility существующего `extinguisher` intent `bind`; новые враги, intents, cards и карты не добавляются.

## Решение пользователя

Выбран **вариант A**: уже `immobilized` герой исключается из eligible targets для `bind` через `targetRules.filters.excludedStatuses`. Интервал `bind` остаётся 12 секунд, длительность `immobilized` — 15 секунд согласно [DR-C-008](./22-step-c-status-immobilized.md) и [docs/05](./05-vertical-slice.md). Production roster, runtime priority и fallback-порядок не меняются.

Первоначально предложенный пользовательский критерий для детерминированной проверки — в каждом скользящем 30-секундном интервале за 120 секунд после первого bind найти хотя бы один непрерывный свободный от `immobilized` период в 10 секунд — не выполняется. Для существующего одиночного фиксированного сценария 7,5 секунды (150 тиков) сохранены как **регрессионная нижняя граница: результат не должен быть хуже ранее измеренного**, а не как выведенное из общего gameplay требование. Шаг наблюдения равен 1 тику (50 ms); одно окно содержит 600 тиков (30 секунд), перебраны все 1,801 начала окна. Этот порог относится только к описанному одиночному seed-сценарию; он не задаёт обязательный gameplay-инвариант для произвольного размера группы. Изменение касается только формулировки порога, а не gameplay.

## Реализация и версионирование

Production template `bind` обновлён с version 1 до **version 2**, так как подтверждённое значение target filter изменилось. Добавлено только `immobilized` в `excludedStatuses`; длительности 12/15 секунд и schema/wire shape не изменены. Существующие test-only templates остались без изменений. Изменение каталога повышает глобальный `CONTENT_VERSION` до **`slice.quarantine-gates.v2`** и синхронизирует все visibility projection schemas. Версия различает идентификаторы наборов шаблонов, но сама по себе старые шаблоны не архивирует.

В текущем replay версия не выбирается по историческому `contentVersion`: reducer проверяет события по `IntentTemplate`, загруженным в переданный initial runtime state. Journal intent events содержат `templateKey`, но не template version/contentVersion. Поэтому replay через изменённый текущий catalog не гарантирует воспроизведение старого catalog. **До слоя persistence это не блокирует текущие headless replay tests; перед появлением БД/исторического replay нужно отдельно решить хранение старых templates:** либо сохранять snapshot набора шаблонов вместе с журналом/checkpoint, либо сохранять неизменяемые каталоги по версиям и выбирать нужную версию.

Сравнение версии журнала с текущим каталогом и отказ replay при mismatch в этот PR не входят: это отдельное расширение engine. Его следует оформить отдельным DR вместе с форматом checkpoint. `stateHash` и runtime state shape не меняются.

Когда все допустимые цели для bind заняты контролем, существующий порядок выбора продолжает проверять следующий доступный intent; для одиночного героя в тесте это существующий fallback `hold_position` после того, как `ally_guard` и `move_close` невалидны. Нового fallback или игрового content нет.

## Детерминированные результаты

Engine integration запускает одного героя и одного Extinguisher с фиксированным seed на 120 секунд после первого `status.applied`. Повторные применения проверяются по реальным engine events и не происходят чаще интервала 12 секунд. Строгая проверка перебирает все 1,801 возможных начала окна (каждый тик, 50 ms) для 30-секундных окон, целиком лежащих в observation interval. Результат: минимум longest-free-run по окнам — **150 тиков (7,5 секунды)**; принятый threshold — **150 тиков**, и все окна проходят его. Первоначальные 10 секунд не выполнялись; числовой критерий изменён с явного разрешения пользователя. Bind 12 секунд, статус 15 секунд, исключение выбранной цели и прочие игровые настройки не менялись.

Boundary-тест подтверждает порядок фаз: на точном expiry tick (tick 540 в фиксированном сценарии) `enemies` phase видит героя ещё `immobilized`; новый `bind` героя не выбирает, а запускается действительный существующий fallback `hold_position`. Затем на первом последующем intent-selection времени (tick 840 в данном сценарии, после разрешения 15-секундного hold_position) герой снова выбирается целью bind. Статус истекает штатно в tick 540 и не обновляется на boundary.

### Справочные показатели: четыре героя

Отдельная fixed-seed simulation использует четырёх героев (`hero-1`–`hero-4`) и одного Extinguisher. Для каждого героя измеряется минимум максимальной длины непрерывного незатронутого отрезка среди всех скользящих 30-секундных окон за 120 секунд после первого `status.applied`; окна сдвигаются на 1 тик (50 ms). Во всех **1,801** окнах индивидуальный минимум составил: `hero-1` — **150 тиков (7,5 s)**; `hero-2` — **150 тиков (7,5 s)**; `hero-3` — **150 тиков (7,5 s)**; `hero-4` — **150 тиков (7,5 s)**. Одновременно immobilized были не менее двух героев на **541 из 2,400 observation ticks**, доля **0.22541666666666665 = 22.5416666667% = 541:2400**. Это справочные результаты данного сценария/seed, не общий критерий баланса. Повторный прогон совпал по `stateHash` и последовательностям `status.applied`/`status.refreshed` для каждого героя.

Повторная симуляция с тем же seed и конфигурацией совпадает по `stateHash` и последовательности ticks status applied/refreshed. Полный replay/journal паритет покрывается соответствующими существующими replay integration тестами.

## Исторический replay и persistence — отдельная задача

`CONTENT_VERSION` — идентификатор семантики набора шаблонов, не механизм архивирования. Реальный исторический replay после появления persistence потребует либо сохранять snapshot шаблонов вместе с журналом/checkpoint, либо поддерживать immutable catalogs по версиям. Проверка mismatch версии journal и текущего каталога с отказом replay намеренно не добавлена; её формат/поведение необходимо согласовать отдельным DR одновременно с форматом checkpoint.
